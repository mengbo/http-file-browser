# Design

## Context

服务端现有四个端点（`/api/health`、`/api/list`、`/api/content`、`/api/image`），全部无索引、按请求实时读文件系统。`browse.go` 的 `resolve` 已实现字面 + 物理两层的越界判定，`sortEntries` 已实现「目录在前、大小写折叠排序」的确定性排序。前端是零构建 vanilla JS 单页应用，浏览位置由 `?path=` 表示，视图切换汇聚在 `load()` 单一入口。探索阶段的完整论证见会话记录，此处只留结论与实现取向。

## Goals / Non-Goals

**Goals:**

- 在 `/api/` 分区内新增搜索端点与前端搜索视图，行为由新 capability `search` 完整承诺。
- 与既有契约的最大重叠：复用 `resolve` 的越界判定、`sortEntries` 的排序、现有错误码词汇与 JSON 错误信封，零新错误码。

**Non-Goals:**

- 内容搜索（读文件找关键词）、索引构建、增量更新。
- 结果封顶、分页、截断标志（与想法池「大目录分页」同域，留给独立 Change）。
- Unicode 规范化（NFC/NFD）。
- 搜索结果中携带元信息（size/mtime）。

## Decisions

### D1: 按文件名搜索，不做内容搜索

三种产品形态（视图内过滤 / 文件名递归搜索 / 内容搜索）中选 B：文件名递归搜索。理由：形态对得上 roadmap Change 10 的名字与阶段 2 位置；搜索结果只是「名字 + 路径」元数据，不触碰 `Directory listing response` 的「SHALL NOT 提供内容」之门与 `text-preview` 判定管道，现有六个 capability 零 MODIFIED。视图内过滤是纯呈现层配菜（更适合作 Change 16 的组成部分）；内容搜索是另一个量级（编码检测、大文件、性能），记想法池独立立 Change。

### D2: 作用域以基准位置为基准，命中携带相对根目录完整路径

`/api/search?path=<base>&q=<query>`，`path` 缺省为根目录，与 `/api/list` 的参数缺省约定同形。搜索结果视图与目录视图共用「相对根目录路径」的位置概念，URL 态自然组合为 `/?path=...&q=...`。命中条目的 `path` 是相对根目录的完整路径而非相对基准的短路径：点击命中即导航，不需要客户端再拼基准。渐进收窄免费获得：结果太杂就点进子目录再搜，想要全局就回根目录。放弃的备选：永远全根搜索（丢失子树收窄）、用户可选范围下拉框（UI 复杂度换不来新能力）。

### D3: 匹配语义三件套与既有约定同源

- **子串包含**：`strings.Contains(name, query)`。glob/正则都要处理转义与 URL 编码的互相干扰，零配置工具要的是可预测。
- **大小写不敏感**：`strings.ToLower` 简单折叠，与 `sortEntries` 的排序折叠同源——同一字段上排序与匹配用两套折叠没有道理；同时延续「不用 locale 相关操作」的可复现性纪律。
- **空/缺失查询匹配一切**：`Contains(name, "")` 恒真，实现零特判，空查询自然退化为无过滤的递归列表。与 list「path 缺失返回根目录列表」取最大结果集的先例完全同形，不为「客户端发了不该发的请求」新增错误分支。
- 已知局限：不做 NFC/NFD 规范化。macOS 上 NFD 形态的重音文件名匹配不上 NFC 形态的查询；CJK 名称不受影响。修复需引入 `golang.org/x/text/unicode/norm`，与 ADR-0001 的轻依赖倾向相悖，按「诚实暴露局限」记录而非引入。

### D4: 瘦命中条目，`search` 不染指元信息

命中条目只有 `name` / `type` / `path`。size/mtime 的取值规则（lstat 语义、不可得省略、整秒）是 `directory-browsing` 的 `Entry metadata` 一整个 Requirement 的领地：带上它们要么整段复述（spec 重复），要么交叉引用（capability 间引用是坏味道）。搜索是「定位」不是「展示」，落点视图自有元信息（文件视图本就不显示大小，无信息断档）。响应形状：`{path, query, matches[]}`，`path` 是规范化基准、`query` 回显——响应自描述，与 list 回显规范化路径同一动机。

### D5: 手写深度优先遍历，不用 `filepath.WalkDir`

结果顺序（spec: Result ordering）要求每目录「先自身全部命中、再按目录顺序依次递归各子树」，且目录内顺序与列表一致（`sortEntries`）。`WalkDir` 有两处不合：一是它按纯字典序访问条目、不做目录优先分组；二是它自行决定下钻时机，无法表达「本目录命中先全部输出」。因此手写递归：每层 `os.ReadDir` → `sortEntries` → 迭代输出命中 → 对目录递归。约二十行，换来顺序契约的直接表达与 D6 的语义控制。备选（WalkDir + 事后重排）需要先收集再排序，两段代码不比一段短，且丢失「命中即输出」的流式性质。

### D6: 遍历不跟进符号链接，与越界物理判定是两个独立决定

手写 DFS 用 `DirEntry.IsDir()`（lstat 语义）判目录，符号链接天然不是目录、不被下钻：软链条目自身按名字参与匹配，指向的子树不产生命中，悬空软链可命中不报错。跟进需要自建 visited 物理路径集合做环检测，为一类边角引入真实风险面——与 Change 17 Non-Goal（软链不作第三类条目）同一克制。注意与 Change 17 不冲突：物理越界判定管「直接请求这条路给不给」（`resolve` 继续全量用于基准路径），遍历语义管「搜索走不走」；前者对基准路径不放松，后者对子树不扩展。

### D7: 局部失败局部降级；基准路径失败复用现有词汇

子树内无权限子目录静默跳过（该子树零命中、其余照常），与 `Entry metadata` 的「单条目元信息不可得不使整个列表失败」同一价值观：局部失败局部降级，永不全局失败。不携带「跳过了哪些」的清单——要报告是未来 Change 的事。基准路径自身的失败不走降级：`resolve` 照常返回 `outside_root` / `not_found` / `not_a_directory` / `permission_denied`，`classify` 照常分类，零新错误码。错误信封格式由 `service-startup` 的 JSON error responses 承诺，本 Change 不动。

### D8: 不封顶、不分页、不加索引

本地回环、单用户、根目录由启动者自选：十万文件量级的代价是几百毫秒与若干 MB JSON，可生存。封顶必然引入「保留哪些」的语义（按序前 N 个 + truncated 标志），是真实的响应形状扩张；它与想法池「大目录分页」同域（分页/封顶/截断），值得有需要时独立 Change 一起设计。每次搜索实时遍历、无索引：零配置是项目愿景，索引需要失效策略与启动成本，为本地单用户工具引入索引得不偿失。

### D9: 前端——搜索视图是 `load()` 的第三个分支

- **入口**：header 中加搜索框（`web/index.html`），表单提交触发搜索。输入为空时提交不动作（空查询会展开整棵子树，前端不替用户做这个决定；API 层面的空查询语义仍按 D3 存在，供显式调用）。
- **URL 态**：`/?path=<base>&q=<query>`。`navigate` 保持只管目录导航（不带 `q`）；搜索提交单独 pushState。`load()` 增加分支：URL 带 `q` 时请求 `/api/search` 并渲染结果视图，否则走既有列表/内容/图片分派。前进/后退因此天然在三类视图间正确切换。
- **结果行**：名称 + 所在目录 + 类型，与列表条目同构（`textContent` 不变量沿用）。所在目录从 `path` 剥掉末段得到，基准为根时显示根的绝对位置；类型沿用 `entry`/`entry-directory` 式的样式区分，不引入图标。
- **点击命中**：目录命中走 `navigate(path)` 进列表，文件命中走 `navigate(path)` 进既有预览分派（`load()` 的 not_a_directory → content/image 分支天然处理）——搜索结果的点击与列表条目的点击是同一条路。
- **空态**：`matches` 为空时呈现「无命中」说明（复用 `#empty` 的呈现思路），错误仍走 `#error` + `ERROR_TEXT` 机器可读分支。

## Risks / Trade-offs

- [NFC/NFD 不规范化导致带重音文件名漏配] → spec 不承诺规范化，design 如实记录；CJK（本工具的主要使用场景）不受影响；真有诉求时立独立 Change 引入 norm 库。
- [不封顶：超大子树返回慢、响应大] → 本地回环单用户可生存；前端一次性渲染大量 DOM 在极端量级会卡——与列表视图同构的已知边界，随「大目录分页」Change 一并处理。
- [软链子树搜不到，用户可能疑惑] → spec Scenario 已诚实声明该行为；界面对软链条目照常可点，点进去按既有物理判定工作，无静默谎言。
- [遍历期间文件系统变化（TOCTOU）] → 与列表端点同一现实：ReadDir/ReadDir 之间的变化不保证一致快照；`ReadDir` 失败的子目录按 D7 跳过，不会让搜索崩溃。
- [手写 DFS 忘了某条失败路径] → spec 每条 Scenario 对应一个确定性测试（沿用 `browse_test.go` 的 tempdir + httptest 模式），软链/悬空链/无权限子目录均有 fixture 可构造。

## Migration Plan

纯增量：新端点、新前端分支，零存量行为修改。无部署迁移；回滚即还原该 Change 的提交。
