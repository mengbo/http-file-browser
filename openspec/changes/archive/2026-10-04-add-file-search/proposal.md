# Proposal

## Why

阶段 2（增强预览）只剩「搜索/过滤」一项未落地。用户在多层级目录里找一个文件时，目前只能逐层点进去翻列表；需要一个按文件名在子树范围内递归定位条目的搜索能力。本 Change 只做**按文件名搜索**——内容搜索（读文件内容找关键词）是另一个量级的能力，涉及文本判定管道与性能问题，记入想法池留待独立 Change。

## What Changes

- 新增 `/api/search` 端点：接受基准位置 `path` 与查询词 `q`，在基准位置的子树内按名称递归匹配，返回命中条目列表。
- 匹配语义：名称子串包含，大小写不敏感（与 `List ordering` 同一套简单折叠）；`q` 缺失或为空时匹配一切（与 `/api/list` 的 `path` 缺省约定同形，空查询自然退化为无过滤的递归列表）。
- 命中条目为瘦条目：`name` / `type` / `path`（相对根目录的完整路径），不带大小与修改时间——搜索是「定位」不是「展示」，元信息仍是 `Entry metadata` 的领地。
- 结果按树序（深度优先）返回，同一目录内命中条目的相对顺序与浏览该目录时的列表顺序一致。
- 遍历行为：不跟进目录符号链接（软链条目本身按名字可命中）；无权限子目录静默跳过、局部失败不全局失败；不封顶不分页。
- 前端新增搜索入口与结果视图：URL 态为 `/?path=<base>&q=<query>`，前进/后退可用；结果行显示名称、所在目录与类型。
- 现有六个 capability 的 Requirement 均不变（零 MODIFIED）：搜索结果只是「名字 + 路径」元数据，不触碰列表「SHALL NOT 提供内容」的门，也不触碰内容判定管道。

## Capabilities

### New Capabilities

- `search`：在基准位置的子树内按文件名递归定位条目的契约——搜索端点与参数缺省约定、名称匹配语义、命中条目形状、结果顺序、越界判定与遍历边界（软链不跟进、无权限子目录跳过）、基准路径失败的机器可读错误。不包含内容搜索。

### Modified Capabilities

（无——`service-startup` 的 HTTP 表面分区已由「`/api/` 区域返回 JSON」覆盖新端点，`directory-browsing` 等现有契约不受影响。）

## Impact

- 后端：`internal/server` 新增 search handler（新文件，如 `search.go`）与路由注册；遍历用 `filepath.WalkDir`，目录内排序复用 `sortEntries`；错误码全部复用现有词汇，无新增。
- 前端：`web/app.js` 新增搜索框与结果视图分支、URL 态扩展（`?q=`）；`web/index.html` 增加搜索框元素；`web/style.css` 增加结果视图样式。
- 无新依赖：不引入 Unicode 规范化库（NFC/NFD 差异记为已知局限）、不引入索引（每次搜索实时遍历）。
- 性能边界：本地回环、单用户、根目录由启动者自选；十万文件量级为可接受的响应延迟与体积。封顶/分页属想法池「大目录分页」的独立 Change。
